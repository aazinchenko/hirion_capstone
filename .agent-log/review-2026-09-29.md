## Findings

| # | File:line | Severity | Rule / aspect | Finding | Recommendation |
|---|---|---|---|---|---|
| 1 | MobileLayoutTest.java:39-41 | Medium | Semantics, KNOWN BUG D3 | `filter(setHasNotText("EN"))` is a case-insensitive **substring** match. A future burger button whose text is "Menu" or "Open" contains "en" and would be filtered out. The test would then keep throwing, so it would keep "passing" as KNOWN BUG D3 even after the bug is fixed. Also, `setExpanded(false)` only matches buttons that actually have `aria-expanded="false"`. A burger without that attribute is never found. | Exclude the language button by exact text, e.g. `setHasNotText(Pattern.compile("^EN$"))`, or better, exclude by exact accessible name. Drop `setExpanded(false)` or accept buttons without aria-expanded. |
| 2 | FooterLegalTest.java:96-100 | Medium | Semantics, KNOWN BUG D1 | The check is `noneMatch(valid)`: it fails only when **no** mailto on the whole page is valid. If a valid mailto appears anywhere else, e.g. a footer `hello@hirion.ch`, the test stops throwing and reports D1 as "fixed" while `mailto:[FILL: ...]` is still on the page. The description says "Imprint email is a valid mailto link". | Fail if the list is empty **or any** href is invalid (`allMatch`). Ideally scope the check to the imprint content (`main`), not the footer. This makes the check stricter, not weaker. |
| 3 | AuthPagesTest.java:64-70; FooterLegalTest.java:81-88; LocalizationTest.java:91-97 (via switchTo, :24); MobileLayoutTest.java:32-47 | Medium | KNOWN BUG robustness | Preconditions in the known-bug tests throw the same `AssertionFailedError` as the defect assertion. Examples: `h1("Imprint").isVisible()`, `switchTo("DE")` asserting the DE button, `field("Email")` missing (hasAttribute times out), the "Sign in" link being renamed. If any of these breaks, the test still "passes" as the known bug and hides a real regression. | Add `expectedExceptionsMessageRegExp` that matches the specific assertion (attribute name / locator). Or check preconditions with `org.testng.Assert`: it throws plain `AssertionError`, which does not satisfy `expectedExceptions = AssertionFailedError.class`. |
| 4 | AuthPagesTest.java:68-69 | Low | KNOWN BUG D5 | Two assertions: if only the Email autocomplete is missing, the Password check never runs. A partial fix (Email fixed, Password not) goes unnoticed until the next run. | Split into two tests (email / current-password), both marked D5. |
| 5 | AuthPagesTest.java:80 | Low | Locator scope | `role(LINK, "Sign in")` searches the whole page on /forgot-password. If a header "Sign in" link is ever added there, this becomes a strict-mode violation. | Scope it to `page.getByRole(AriaRole.MAIN)`. |
| 6 | FooterLegalTest.java:96-97; QualityTest.java:40-43 | Low | Rule bypass | `page.evaluate("document.querySelector(...)")` uses raw CSS selectors (`a[href^="mailto:"]`, `meta[name="description"]`, `link[rel="canonical"]`). CheckLocatorRules does not catch this because it only looks for `.locator(`. For head metadata this is the pragmatic choice, but it is still a CSS query without a `// locator-exception:` comment. | Add `// locator-exception: <head> metadata / mailto href list` comments. For the mailto list, consider `page.getByRole(AriaRole.LINK).evaluateAll(...)` filtered by href. |
| 7 | FooterLegalTest.java:47-54 | Low | Semantics | "Internal footer links respond" checks a hard-coded path list, not the hrefs actually in the footer. A new or renamed footer link is not covered. | Collect the internal hrefs from `getByRole(CONTENTINFO).getByRole(LINK)` and request each one. |

## Verdict

**APPROVE**, with non-blocking follow-ups.

No AGENTS.md rule is broken, CheckLocatorRules passes, safety rules are met, and no KNOWN BUG test was weakened. Findings 1-3 (Medium) should be fixed in a follow-up change. They do not break current behaviour, but they could make a known-bug test report the wrong status: #1 and #2 could hide a real fix or keep a bug looking fixed, and #3 could hide an unrelated regression behind an "expected" failure.
